DATADOG · INITIAL CODING INTERVIEW

Make your reasoning visible.

One hour: 5 minutes to introduce yourself · 45 to code · 10 for your questions. Notes from the candidate guide, reviewed 17 October 2026.

Clarify → explain → build → run → improve.

Get a correct solution running. Say why each important choice works. Test before you optimise.

Approach

State the invariant. Explain time, space, and one alternative.

Completeness

Run the code early. Check empty input, one item, duplicates, and boundaries.

Readability

Use clear names, small functions, and familiar Go libraries.

The guide gives these three signals roughly equal weight.

A practical 45-minute plan

This is a practice schedule, adapted from the guide's approximate ranges.

  1. 0–4 min · Understand. Restate input and output. Ask about size, validity, ordering, and mutation where relevant. Confirm one example.
  2. 4–8 min · Plan. Compare a simple approach with a better one. Pick one and state why it works.
  3. 8–32 min · Build. Write a small working version. Run it as soon as possible. Explain decisions, not every keystroke.
  4. 32–40 min · Harden. Test boundaries and failure cases. Fix bugs and simplify names.
  5. 40–45 min · Discuss. Defend complexity, state limitations, and explain the next improvement.
What to say, and what to do when stuck

Open: “I need to return X from Y. What are the input limits? Can the input be empty? My approach is A because B. The invariant is C.”

If stuck: name the exact obstacle. Try a simpler working approach. Trace a tiny example or print state. Use the interviewer's hint.

Before finishing: test the final version, include sorting and auxiliary storage in the cost, and identify any unresolved case.

The guide permits language documentation and API references. Confirm the coding platform in the invitation; ask the recruiter for practice access if needed. Check Chrome, audio, and connection beforehand.

Four questions to bring · choose two or three

These are prompts inspired by public engineering posts, not assumptions about this team's implementation. Start with the topic closest to your interviewer's work.

  1. Late data and correctness. “I read your post on data completeness. How does your team decide when data is complete enough for a signal, and what happens when late data changes the result?” Read: data completeness ↗

    The post explains why arbitrary delays and replay make watermark-based completeness difficult.

  2. Backfills and live traffic. “Your Streaming Platform uses separate lanes for different priorities. How do you keep reprocessing or backfills from delaying live signal detection?” Read: Streaming Platform ↗

    Follow up on the metric that shows whether this isolation works.

  3. Delivery guarantees. “The Streaming Platform post describes at-least-once delivery and relaxed processing order. Which guarantees do your signal pipelines need, and where do you handle duplicates or ordering?” Read: consumer semantics ↗

    Connect this to your own Kafka or Flink experience if relevant.

  4. Safe changes. “I read about distributing configuration to thousands of containers. How does your team validate and roll back a model or configuration change that affects signal quality?” Read: configuration delivery ↗

    The post covers configuration distribution; the model-rollout question is an extension for this role.

What to practise next

These are priorities to verify from our practice so far, not a claim that an untested skill is missing.

  1. First: one unseen medium problem, aloud, in 45 minutes. Use a blank editor. Score approach, completeness, and readability separately. Record the first successful run and time left for tests.
  2. Then: a short Go fluency drill. Use maps, slices, sorting, string conversion, and container/heap without copying a template. Explain byte versus rune and slice length versus capacity.
  3. Revisit fragile boundaries. Binary-search endpoints, prefix-frequency counting, heap child bounds, and interleaved push/pop. Explain the invariant before coding.
  4. For later rounds: design a Kafka/Flink signal pipeline with replay, late events, state recovery, tenant isolation, and cost limits. Prepare two short experience stories with your decision, trade-off, result, and lesson.

Keep breadth across arrays, strings, maps, two pointers, and trees. DP and backtracking remain outside this quick reference; revisit their priority after the mock.

1. Match the task to a tool

2. Check the operation cost

n = item count; h = tree height; V/E = graph vertices/edges. Constant-time map costs assume short keys.

Common costs in Go
StructureOperation and timeWatch for
SliceIndex O(1); append amortized O(1); insert/delete in the middle O(n).Growth can allocate and copy O(n) items.
StringByte index and substring slice O(1); concatenate O(n + m).Immutable. An index gives a byte, not a Unicode character. Slices may retain the original storage.
Linked listFind a node O(n); relink known adjacent nodes O(1).Singly linked deletion usually needs the previous node.
Map / setKey lookup, insert, delete: expected O(1). Scan values O(n).Hashing a long key costs time. A Go set can use map[T]struct{}.
Stack / queueStack push or queue append: amortized O(1); pop, front, peek O(1).Use a head index or ring buffer for a queue; do not shift all items.
BSTSearch, insert, delete O(h).Balanced: O(log n). A chain: O(n).
HeapPeek O(1); push/pop O(log n); build with heap.Init O(n).Only the root is guaranteed to be the minimum in a min-heap.
TraversalTree O(n); adjacency-list graph O(V + E).Assumes O(1) work per visit. Tree DFS space O(h); BFS O(width). Graph visited state O(V).
Search / sortBinary search O(log n); comparison sorting usually O(n log n).Include the cost of each check. Plain quicksort can take O(n²).

4. Use a short interview checklist
  1. Introduce: give a brief, relevant background.
  2. Clarify: restate the task, constraints, and one example.
  3. Plan: explain the invariant and expected cost.
  4. Implement: name state clearly and explain key choices.
  5. Test: trace a small case, then boundaries and duplicates.
  6. Review: justify correctness, time, space, and trade-offs.
  7. Close: ask prepared questions about the work and team.

CHOOSE THE RIGHT TRAVERSAL

DFS or BFS?

DFS · finish a path

Use a stack for inorder, subtree results, or path state. A tree uses O(h) stack space.

BFS · finish a level

Use a queue for levels or shortest paths in an unweighted graph. A tree uses O(w) queue space.

For island counting, either works. In both cases, mark a cell when you discover it. h = tree height; w = maximum level width.
